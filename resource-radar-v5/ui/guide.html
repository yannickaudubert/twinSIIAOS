Guide d'utilisation

Utiliser le Radar sans devenir archiviste de technologies.

Le but n'est pas d'accumuler des favoris. Utilisez le Radar pour réduire progressivement un espace de possibles : besoin → approche → options comparables → preuves → décision.

Le parcours court

Si vous n'avez que cinq minutes.

01Décrivez le besoinUne capacité attendue, pas un nom d'outil.
02Choisissez l'approcheComprendre les familles de solutions possibles.
03Ouvrez un paysageComparer uniquement des responsabilités similaires.
04Ouvrez une ficheRôle, limites, licence, preuves, provenance.
05Décidez du prochain gesteIgnorer, surveiller, tester, comparer ou contextualiser.
Cas 1

« Je connais déjà le nom d'une solution. »

Exemple : Qdrant, LangGraph, vLLM, Docling.

Recherche directe

Ce qu'il faut lire

Nature réelle, rôle architectural, licence, état de preuve, dernière vérification, alternatives comparables et point d'attention principal.

Ce qu'il ne faut pas conclure

Stars, activité GitHub ou présence dans le Radar ne signifient pas « recommandé ». Cherchez le niveau de preuve et le contexte.

Cas 2

« J'ai un problème mais je ne connais pas la solution. »

Commencez par la capacité, puis regardez les approches. Exemple : « comprendre des PDF complexes » peut conduire à OCR, parsing structuré, document VLM ou combinaison hybride.

Capacités
Capacité

Ce qu'il faut pouvoir faire

  • décrit le résultat attendu ;
  • reste indépendant d'un fournisseur ;
  • peut être couvert par plusieurs approches.
Approche

La manière de résoudre

  • peut évoluer très vite ;
  • change parfois toute l'architecture ;
  • doit être comparée avant les produits.
Ressource

L'implémentation concrète

  • logiciel, framework, modèle ou service ;
  • porte une licence et des contraintes ;
  • peut être testée, intégrée ou rejetée.
Cas 3

« J'hésite entre plusieurs options. »

Avant de comparer des noms, vérifiez qu'ils remplissent réellement le même rôle. Un moteur de workflow durable n'est pas l'équivalent d'un builder low-code ; une base vectorielle n'est pas un framework RAG.

Paysages
Règle simple :

si deux solutions ne peuvent pas remplacer la même responsabilité dans votre architecture, elles ne doivent probablement pas être classées dans la même colonne de comparaison.

Cas 4

« Je dois vérifier si une conclusion est solide. »

Lisez l'état de preuve avant le classement ou la tendance.

Comprendre les preuves
Observé

Faits publics vérifiés : dépôt, licence, documentation, release, activité, source officielle.

Ne vaut pas test
Installé

La ressource a été effectivement installée dans un environnement déclaré.

Ne vaut pas qualification
Testé

Un protocole ou cas d'usage a produit des résultats vérifiables.

Preuve contextualisée
Qualifié

Les résultats sont suffisamment étayés pour soutenir une recommandation dans un contexte explicite.

Conclusion datée
Cas 5

« Je veux tester ou récupérer la ressource. »

La vue Acquérir conserve la logique opérationnelle de la V3 : source officielle, résolution d'artefact, téléchargement, miroir, hash, manifeste et bridge local lorsque disponible.

Acquérir

Avant le téléchargement

Vérifiez licence, version, source, format et compatibilité. Le Radar doit conserver la provenance avec l'artefact.

Après le téléchargement

Hash, manifeste, environnement et résultat de test doivent rester rattachés à la ressource pour éviter une qualification sans traçabilité.

Cas 6

« Je dois prendre ou défendre une décision professionnelle. »

C'est ici que la valeur Expert commence : votre matériel, votre SI, vos compétences, vos contraintes de sécurité, vos coûts et votre trajectoire peuvent inverser le classement général.

Voir le Pass Conseil 8 h
Avant Expert

Vous pouvez déjà établir

  • la nature et le rôle des options ;
  • les sources et licences ;
  • les différences d'approche ;
  • les preuves publiables ;
  • les alternatives et limites générales.
Avec Expert

Le contexte devient un calcul de décision

  • critères pondérés ;
  • risques d'intégration et d'exploitation ;
  • fit matériel / organisation / gouvernance ;
  • architecture et migration ;
  • recommandation argumentée et restitution.
Bonnes pratiques

Quatre réflexes qui évitent les mauvaises lectures.

01

Regardez la date

Une conclusion technique vieillit. Vérifiez toujours quand elle a été observée ou testée.

Fraîcheur avant certitude
02

Lisez le niveau de preuve

« Observé » ne signifie pas « testé ». « Testé » ne signifie pas « adapté à votre contexte ».

Preuve avant classement
03

Comparez les mêmes rôles

Les catégories marketing mélangent souvent des responsabilités différentes.

Architecture avant logo
04

Gardez la provenance

Source, licence, version, test et décision doivent rester reliés.
